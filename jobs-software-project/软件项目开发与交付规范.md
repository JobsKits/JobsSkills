## 🔥 <span id="前言">前言</span>

本规范适用于软件项目从需求摸排、开发评审、实现与测试，到部署、验收、交接和维护的完整过程。保留“需求摸排、三级验收、前端产品包与技术栈、后端技术栈与数据库、后端部署方案”五个主体章节，并补齐工程、交付与运维要求。

| 项目 | 说明 |
| --- | --- |
| 文档版本 | V1.2 |
| 编制及技术资料核验日期 | 2026 年 11 月 2 日 |
| 前端默认规则更新日期 | 2026 年 11 月 3 日；未重新核验其它技术版本 |
| 适用对象 | 需求方、产品、设计、开发、测试、部署、运维及验收人员 |
| 条款用语 | “必须”表示必备要求；“应”表示通常执行、例外需说明；“可”表示按项目选择 |
| 项目落地方式 | 每个项目建立实施基线，填实交付范围、验收等级、平台版本、性能指标、责任人和例外项 |
| 版本维护 | 操作系统、框架及第三方服务存在变化时，重新核验并更新项目基线；不能只修改文档日期 |

通用规范不替代具体项目的需求文档和合同约定。通用要求存在项目例外时，必须记录原因、影响、替代措施及确认人。项目中尚未填实的容量、版本和性能指标，不得作为已完成验收的依据。

根据用户原始需求生成具体项目文档时，没有提供且无明确默认规则的信息必须留白；有依据但尚不确定的内容以红字及稳定编号标注，例如 `<span style="color:#d32f2f;">【不确定 Q-001】具体内容与依据</span>`。用户补填后，保留其输入并进行完整性、一致性和业务闭环回归，未解决项继续标红。前端未特别说明时默认采用标准型（平台原生／标准 Web），记录“按 Skill 默认”，无需再询问原生还是跨平台；用户明确指定通用型（跨平台）或按端混合时遵从指定。默认规则只适用于需求范围内的目标端，不自动确定具体语言、框架或版本，也不改变既有项目已确认的方案。

本文中的“完整交付”以已确认的本期范围为准；未来规划应单独列出，不得以未完成页面、占位接口或演示数据替代本期应交付的业务能力。

## 一、<span id="requirements">需求摸排</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

### 1.1、<span id="requirements-document">需求文档</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 1.1.1、<span id="original-requirements">用户原始需求与溯源</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

用户原始需求通常模糊、简短，并可能附带案例参考。项目需求文档必须直接保留用户原文，同时登记提出人、提出日期、来源、参考链接、截图及附件。易失效的案例在允许保存的范围内保留必要快照。

产品解释、技术推断、后续澄清和确认结论应另行记录，保留各自来源及状态。原始表述有变化时保留修订记录，保证可以追溯“谁在何时提出了什么、最终确认了什么”。

#### 1.1.2、<span id="roles-permissions">角色与权限定义</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

建立角色与权限矩阵，至少明确角色职责、页面访问、功能操作、数据范围、敏感字段及后台管理权限。存在组织、门店或多租户时，明确数据归属和隔离规则。

权限必须由后端校验，前端隐藏按钮只承担界面展示职责。覆盖未登录、登录过期、账号停用、角色变更、越权访问及跨租户访问等情况。

#### 1.1.3、<span id="business-flows">核心业务流程与异常闭环</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

逐项说明流程的参与角色、前置条件、输入、处理规则、状态转换、输出及终止条件。业务流程图应与文字规则保持一致，复杂流程使用可编辑的状态图或时序图表达。

必须覆盖成功、失败、取消、拒绝、超时、重复提交、重试和必要补偿。涉及订单、支付、退款、库存、审批或结算时，应明确并发处理、金额精度、回调顺序和一致性规则。

涉及第三方能力时，明确账号资质、接口权限、沙箱与正式环境、费用、配额、限流及失败处理；将不可由开发方独立完成的条件列为项目依赖。

#### 1.1.4、<span id="milestones">分标段与分阶段项目里程碑</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

每个标段或阶段必须明确交付范围、交付物、计划日期、依赖、负责人、验收人、验收期限、目标验收等级及进入下一阶段的条件。涉及多个承接方时，明确接口归属、集成顺序和联调责任。

里程碑应交付可检查的结果，例如已确认需求、可操作原型、完成联调的业务闭环或可安装版本。客户资料、账号资质、第三方接口等延期的影响及处理方式应提前约定。

#### 1.1.5、<span id="risks-advice">风险提示与开发建议</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

风险清单应包括技术可行性、平台能力、第三方依赖、性能与容量、数据安全、许可、交付周期、持续费用和维护成本。每项风险登记影响、触发条件、应对措施、负责人及剩余风险。

开发建议应说明依据、成本和适用条件。对高风险或尚不确定的能力，安排必要的可行性验证，再确定交付承诺和排期。

#### 1.1.6、<span id="scope-priority">项目目标、范围与优先级</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

明确目标用户、要解决的问题及成功条件。分别列出本期包含、后续规划和明确排除的功能；各项需求设置唯一编号、优先级和所属里程碑。

页面、接口、权限、数据迁移及部署任务均应能映射到需求或交付项。待确认事项必须记录负责人和确认期限；阻塞实现或验收的事项，应在对应阶段开始前解决或正式调整范围。

#### 1.1.7、<span id="nonfunctional-requirements">非功能需求</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

按业务填实性能、容量、稳定性、安全、兼容性、易用性、无障碍、多语言、时区、数据保留及恢复要求。性能必须同时约定硬件、网络、数据规模、负载模型和统计方法，参见[验收指标基线](#acceptance-metrics)。

#### 1.1.8、<span id="traceability">需求追溯矩阵</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

建立“原始需求 → 需求编号 → 页面／接口／业务规则 → 测试用例 → 验收证据”的对应关系。每项本期需求均能定位实现结果和验证结果，避免需求漏实现或测试无法解释覆盖范围。

#### 1.1.9、<span id="change-control">需求基线与变更管理</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

需求确认后形成版本基线。新增、删除或修改需求时，记录原因、受影响功能、数据、接口、测试、工期和费用，经约定负责人确认后实施。

缺陷修复与需求变更分别管理。已确认需求未正确实现属于缺陷；范围调整按变更处理。争议项保留依据和处理结论。

### 1.2、<span id="development-review">开发评审</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 1.2.1、<span id="architecture-review">后端技术架构与容量规划</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

评审服务边界、部署拓扑、调用关系、业务负载、数据增长、任务调度、扩容及故障处理。根据需要评估缓存、消息队列、搜索及对象存储，并说明引入理由与运维成本。

分库分表属于容量与架构评估结论，不作为所有项目的默认前提。确有需要时，明确分片键、路由、事务边界、跨分片查询、唯一标识、扩容迁移及备份恢复方案。

#### 1.2.2、<span id="database-review">数据库设计</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

提供完整表清单、核心表结构和数据关系；所有实际交付的表应补齐字段字典。至少说明字段类型、可空性、默认值、主键、索引、唯一约束、关联关系、数据归属及用途。

同步评审事务、金额与时间精度、编码与排序、审计、删除与归档、数据迁移、备份及清理。数据库结构变更以可追溯的版本迁移管理。

#### 1.2.3、<span id="test-review">测试用例与测试计划</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

用例应包含需求编号、前置条件、测试数据、操作步骤、预期结果、优先级及适用环境。覆盖正常、异常、边界、权限、并发、弱网、安装升级、回滚恢复和平台兼容性；不适用项说明原因。

明确测试范围、设备与环境、测试数据准备、执行责任、缺陷分级及验收准入条件。关键业务应配置适当的单元、集成、接口或端到端自动化验证。

#### 1.2.4、<span id="frontend-review">前端与交互评审</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

评审页面清单、交互原型、导航、表单校验、权限反馈、空数据、加载、失败、离线及恢复状态。明确各端窗口或屏幕范围、键盘与触控方式、主题、字体缩放及无障碍要求。

对跨端复用和平台差异逐项评估；支付、推送、定位、扫码、相机、文件、后台运行等关键能力，应在目标平台提前验证。

#### 1.2.5、<span id="api-review">接口与集成评审</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

明确请求与响应、认证授权、错误码、分页、上传下载、超时、重试、幂等、限流、回调和版本兼容。接口变更需要同步受影响客户端、测试及文档。

#### 1.2.6、<span id="review-decisions">评审结论与成本确认</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

形成“通过、有条件通过、需重新评审”的明确结论，并记录遗留项、负责人和期限。开发、测试、部署、商店发布及持续维护的成本分别估算；免费软件与第三方免费额度不等于零运行成本。

## 二、<span id="acceptance">三级验收标准（强度逐级递增）</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

高一级包含前一级全部要求。基本安全、数据正确性和必要工程规范从开发开始执行，验收等级用于确定验证深度和交付能力，不能成为延期处理基础质量问题的理由。

### 2.1、<span id="acceptance-basic">一级：基础可运行</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 2.1.1、<span id="basic-functional">业务完整性</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

本期已确认范围内的功能必须完成；各功能的主流程及关键异常路径形成逻辑闭环。不得以未完成开发、静态占位或虚假成功反馈通过验收；调整范围必须先完成需求变更。

#### 2.1.2、<span id="basic-quality">基础质量与冒烟测试</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

在约定环境中，冒烟用例和主流程用例全部通过，具备安装、启动、登录、核心读写和必要重启验证。测试范围内不得有未解决的崩溃、流程阻断、越权、数据损坏及关键计算错误。

允许不影响操作的界面微调和适配瑕疵，并列入遗留问题清单。遮挡关键按钮、导致内容不可读或无法完成操作的适配问题不属于可放行的视觉瑕疵。

### 2.2、<span id="acceptance-commercial">二级：可商用</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 2.2.1、<span id="commercial-tests">全量测试与缺陷门槛</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

“全量测试”指已评审测试基线中的用例全部执行，关键业务及阻断级用例全部通过，其余用例达到预先约定的通过率和放行条件。未执行、被阻塞和不适用的用例分别记录，不计为通过。

不得遗留阻断运行、严重安全风险、核心数据错误或影响关键交易的缺陷。其余问题必须明确影响、临时措施、修复期限和确认人。

#### 2.2.2、<span id="commercial-performance">性能与使用体验</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

在约定硬件、网络、数据规模及负载下达到性能基线。允许存在已记录且不超过约定阈值的体验问题；“允许卡顿”必须细化为可测量的启动时间、响应时间、界面流畅度或资源使用上限。

#### 2.2.3、<span id="commercial-operation">上线与运行能力</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

具备实际部署、配置管理、日志、健康检查、必要告警、备份恢复、升级回滚和故障处理能力。完成正式依赖、账号、证书、资源配额及发布资质的核对；实际范围涉及的数据、隐私及平台要求应完成对应检查。

### 2.3、<span id="acceptance-industrial">三级：工业化标准</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 2.3.1、<span id="industrial-quality">易用性、健壮性、封装性与可移植性</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 质量维度 | 必须明确的检查依据 |
| --- | --- |
| 易用性 | 核心任务完成路径、错误提示、可恢复操作、交互一致性及适用的无障碍要求 |
| 健壮性 | 弱网、依赖故障、超时、重复请求、进程重启和资源不足等场景下的行为及恢复证据 |
| 封装性 | 清楚的模块职责、稳定接口、依赖方向及必要测试；避免业务规则散落和重复实现 |
| 可移植性 | 约定系统与 CPU 架构上的构建、安装和运行验证；配置与数据可迁移，路径不绑定开发机 |
| 可维护性 | 代码评审、依赖管理、自动化检查、可复现构建、运行诊断和维护文档 |

#### 2.3.2、<span id="industrial-evidence">工程与运行证据</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

通过约定的持续集成、关键业务回归、构建发布、升级恢复及故障演练；根据业务验证容量扩展、长期运行和灾备目标。工业化不要求所有项目采用微服务、分布式数据库或复杂集群，架构规模应与业务相匹配。

### 2.4、<span id="acceptance-metrics">统一验收指标与证据</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 2.4.1、<span id="metrics-baseline">指标基线</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

每个项目在测试前填实下表；数值由业务和验证结果决定，不以统一的无依据数值套用所有项目。

| 指标类别 | 项目必须填写的内容 |
| --- | --- |
| 环境 | 系统与构建号、CPU 架构与能力、内存、磁盘、网络、软件版本及部署方式 |
| 负载 | 在线用户数、并发请求数、每秒请求数、读写比例、峰值持续时间；分别定义，避免混用 |
| 数据 | 初始数据量、数据分布、附件规模及预计增长量 |
| 性能 | 客户端启动、接口与端到端响应时间的统计口径，P95 等分位数及错误率阈值 |
| 稳定性 | 持续运行时间、资源上限、异常重试与恢复条件 |
| 恢复 | 可容忍的数据丢失时间（RPO）、目标恢复时间（RTO）及验证方式 |
| 缺陷 | 严重程度定义、各等级允许遗留数量及例外确认规则 |

#### 2.4.2、<span id="evidence-classification">验证状态与真实业务证据</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

用例状态统一区分“通过、失败、未执行、阻塞、不适用”。报告附版本、执行日期、环境、数据、步骤、日志或截图及遗留问题。

构建成功、安装成功、真机或目标环境业务通过、正式渠道发布成功分别记录。模拟数据、沙箱、离线演示及真实联调分别标明；正式服务端持久化、权限和交易能力必须提供对应环境的真实证据。

### 2.5、<span id="acceptance-process">验收流程与结论</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

验收前冻结候选版本及范围，完成测试、交付物核对和风险登记，再由约定验收人给出通过、有条件通过或不通过的结论。有条件通过必须列出允许遗留事项、期限和责任人，不得豁免本等级的阻断条件。

修复后执行受影响范围的回归，并保留复验结论。有限测试只能证明已检查范围内的结果，不能写成对所有未知场景“永不崩溃、绝无错误”的保证。

## 三、<span id="frontend-stack">前端产品包与技术栈</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

用户未特别说明时，各目标端默认采用原生方案：桌面端、移动端采用各平台原生技术，Web 采用标准 Web，小程序采用官方原生方案。跨平台或按端混合方案按用户明确指定采用。每个产品端记录实际路线与采用依据；本节列出可选平台，不代表全部纳入本期交付。要求同时交付原生版与跨平台版时，分别列入范围、排期和验收矩阵。

### 3.1、<span id="desktop">PC 端桌面应用程序</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

目标平台包括 [**Windows**](https://www.microsoft.com/windows) 与 [**macOS**](https://www.apple.com/macos/)。典型运行产物分别为 `*.exe` 和 `*.app`；安装器可根据发布渠道另行约定。

#### 3.1.1、<span id="desktop-native">平台原生方案（默认）</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

macOS 可采用 [**Swift**](https://www.swift.org/)、[**Objective-C**](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/ProgrammingWithObjectiveC/Introduction/Introduction.html) 构建原生界面，并按需通过 [**C++**](https://isocpp.org/) 实现底层能力。Windows 可采用 [**C#**](https://learn.microsoft.com/dotnet/csharp/) 及对应桌面框架，按需结合 C++。语言选择与实际界面、系统接口方案需一并评审。

#### 3.1.2、<span id="desktop-python">跨平台方案：[**Python**](https://www.python.org)</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

用户明确采用 Python 跨平台方案时，根据交互和授权要求选择图形框架，分别为 Windows、macOS 及约定 CPU 架构构建和验证。面向普通用户的交付包应携带所需解释器、库和资源，尽量实现安装后直接运行。

采用 [**PyInstaller**](https://pyinstaller.org/en/stable/operating-mode.html) 等合适打包方案时，用户不必预装 Python。源码或脚本分发模式需要 Python 时，应单独说明版本、安装与依赖步骤。PyInstaller 产物与构建平台有关，不能将一个平台的包直接当作另一平台的成品。

#### 3.1.3、<span id="desktop-packaging">桌面交付与兼容性</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

交付内容明确最低系统、CPU 架构、安装与卸载、签名或公证要求、升级、数据目录、日志及迁移方式。Python 跨端图形软件提供白天、黑夜和跟随系统三种主题，并覆盖实际控件。

Windows 10 及以上版本按已验证矩阵纳入兼容范围。Windows 10 普通版本已于 2025 年 10 月 14 日结束支持；保留测试支持时注明具体版本与安全更新状态，扩展安全更新及长期服务版本按其独立生命周期核验。参见 [Microsoft 生命周期说明](https://learn.microsoft.com/en-us/lifecycle/announcements/windows-10-22h2-end-of-support-update)。

### 3.2、<span id="mobile">手机移动端</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

目标平台包括 [**Android**](https://developer.android.com/)、[**iOS**](https://developer.apple.com/ios/) 与 [**HarmonyOS**](https://developer.huawei.com/consumer/cn/)。各平台版本、设备类别、架构与发布渠道单独登记。

#### 3.2.1、<span id="mobile-native">平台原生方案（默认）</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

Android 可采用 [**Kotlin**](https://kotlinlang.org/) 或 [**Java**](https://dev.java/)；iOS 可采用 Swift 或 Objective-C；HarmonyOS 以目标版本支持的 [**ArkTS**](https://developer.huawei.com/consumer/cn/arkts/) 方案为主，[**仓颉（Cangjie）**](https://cangjie-lang.cn/) 等方案需按目标系统和工具链验证可用能力。不同语言的 UI、生态与插件能力不能默认等价。

iOS 选用原生方案时，必须按语言采用 Jobs 对应基础工程与[原生工程专项要求](#ios-native-baseline)。

#### 3.2.2、<span id="mobile-flutter">跨平台方案：[**Flutter**](https://flutter.dev/)</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

用户明确采用 Flutter 跨平台方案时，Android 与 iOS 使用经项目验证的 Flutter 工具链。HarmonyOS 采用相应鸿蒙／OpenHarmony 适配项目，并锁定仓库、版本标签或提交、引擎、开发工具及插件版本；不能直接承诺 Flutter 官方主线覆盖鸿蒙全部能力。

鸿蒙适配应分别核验目标 HarmonyOS 设备与系统，不能仅凭 OpenHarmony 适配声明推定所有目标均兼容。构建、签名、安装、真机业务和关键插件都必须完成对应验证。依据：[Flutter 官方平台矩阵](https://docs.flutter.dev/reference/supported-platforms)、[Flutter 鸿蒙适配项目](https://gitcode.com/CPF-Flutter/flutter_flutter)。

#### 3.2.3、<span id="mobile-packages">移动端产品包与发布</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 平台 | 典型产物 | 交付说明 |
| --- | --- | --- |
| Android | `*.apk`、按渠道提供 `*.aab` | APK 用于安装；AAB 是发布格式，需经相应工具或分发渠道处理生成可安装 APK |
| iOS | 按分发方式提供签名 `*.ipa`、归档或上传构建 | 明确测试、商店或其它适用分发路径、证书及设备权限，不能承诺任意设备直接安装 |
| HarmonyOS | 按目标 SDK 与渠道提供签名 `*.hap`、应用发布包 `*.app` 等 | 区分安装模块与发布打包用途，注明目标系统、签名及安装／上架步骤；此处 `*.app` 与 macOS 应用含义不同 |

Android 格式依据：[Android App Bundle 官方说明](https://developer.android.com/guide/app-bundle/faq)。平台包格式和发布规则以项目采用的官方 SDK 文档为准。

#### 3.2.4、<span id="ios-native-baseline">iOS 原生工程蓝本与专项要求</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

**3.2.4.1、按语言选择工程蓝本。**选用 Objective-C（OC）时，以 Jobs 的 OC 新工程 `JobsOCBaseConfigDemo@ByPods` 为蓝本；选用 Swift 时，以 `JobsBaseConfig@JobsSwiftBaseConfigDemo` 的 UIKit 工程为蓝本。项目记录蓝本来源、采用的提交或版本及裁剪范围，沿用对应的目录、基础层和依赖组织方式；SwiftUI 工程属于单独方案，不能默认替代 Swift UIKit 蓝本。

| 专项 | OC 原生方案 | Swift 原生方案 |
| --- | --- | --- |
| 工程蓝本 | `JobsOCBaseConfigDemo@ByPods`，OC 新工程 | `JobsBaseConfig@JobsSwiftBaseConfigDemo`，Swift UIKit 工程 |
| Jobs 能力复用 | 优先复用 `JobsByPods/` 中适用的 Jobs 自维护模块 | 优先复用 `JobsByPods/` 中适用的 Jobs 自维护模块 |
| DSL | 采用蓝本的创建工厂、`JobsOCDSL`、`JobsModelDSL` 等点语法与链式入口 | 采用 `JobsByUIKit`、`JobsSwiftDSL` 等点语法与链式入口 |
| 依赖管理 | `Podfile`＋`Podfile.deps` 解耦 | `Podfile`＋`Podfile.deps` 解耦 |
| 安装后收尾 | 由 `Podfile` 的相应 hook 调度项目所需脚本 | 由 `Podfile` 的相应 hook 调度项目所需脚本 |
| 约束布局 | [**Masonry**](https://github.com/SnapKit/Masonry) | [**SnapKit**](https://github.com/SnapKit/SnapKit) |
| 业务网络请求 | [**YTKNetwork**](https://github.com/kanyun-inc/YTKNetwork)，复用蓝本已有的 Jobs 请求封装 | [**JobsNetworking**](https://github.com/JobsKits/JobsNetworking) |

**3.2.4.2、尽可能复用 JobsByPods。**开发前盘点蓝本 `JobsByPods/` 已有能力，优先复用适合业务的组件、工具、模型、DSL 和公共封装，避免重复实现。只引入所需模块及其必要依赖，保持公开接口、资源和依赖关系完整；Demo 页面、无关能力及其依赖不机械照搬。第三方、手工托管和生成代码保留来源及许可，不因本地托管就视为 Jobs 自有源码。

**3.2.4.3、DSL 统一采用链式语法＋点语法。**对象创建、属性配置、事件和装配优先通过对应 Jobs DSL 完成；已有封装必须复用，缺失时先核对所属层再补齐。连续配置同一主对象尽量一链完成，每个动作正常分行；链式入口返回可继续调用的当前对象类型。查询、控制流和明确终止动作按真实语义表达，不为表面链式改变业务返回值。OC 与 Swift 沿用各自语言实现和公开 API，不按名称猜测不存在的调用。

**3.2.4.4、Podfile 解耦。**采用 [**CocoaPods**](https://cocoapods.org/) 时，`Podfile.deps` 只维护依赖声明与必要分组，逐条直观列出 Pod、版本或相对路径；安装配置、hook 和外部脚本调度留在 `Podfile` 或其明确加载的安装辅助层。保持 `Podfile.deps` 在 Xcode 的 Pods 根组中与 `Podfile` 相邻、唯一、可打开编辑，并以 Ruby 文件类型显示；不加入编译阶段。

**3.2.4.5、挂载 pod install 后续脚本。**复用蓝本的脚本组织与调度机制，按项目实际需要接入安装后收尾，使用项目相对路径并同步携带必要入口、参数、开关和说明。`post_install` 可在生成的 Xcode 工程写盘前调整配置；依赖工程已写盘结果的收尾放入 `post_integrate`。脚本挂载时机必须与实际 hook 一致，不把文件仅存放在目录里写成已挂载。依据：[CocoaPods hook 官方说明](https://guides.cocoapods.org/syntax/podfile.html#hooks)。

辅助脚本调用先检查文件、权限和执行结果，缺失或失败默认告警并跳过；只有明确约定为强制门禁的检查才阻断安装。脚本可重复执行，记录顺序、日志及产物，不破坏 Pods 工程。挂载变更同时更新脚本说明和项目根 README；不默认引入蓝本中的所有可选增强。

**3.2.4.6、约束库按语言固定。**Jobs 自维护 UI 约束统一采用 OC 的 Masonry、Swift 的 SnapKit，并优先复用其 Jobs DSL 封装。新增业务布局不另起直接使用系统约束或 Anchor 的实现；约束更新与重建按实际布局变化选择，避免冲突。第三方或生成实现继续按所有权边界处理。

**3.2.4.7、网络层按语言固定。**OC 业务 API 统一通过 YTKNetwork 及蓝本已有 Jobs 封装；Swift 业务 API 统一通过 JobsNetworking。环境、认证、错误、超时、取消、重试及演示回退在对应网络层统一组织，业务页面不另建平行请求体系。Swift 的底层实现或兼容目录存在其它库时，不自动成为业务层直接调用或引入该库的理由；可选模块依据目标系统与业务需要选择。

**3.2.4.8、专项验收。**核对蓝本与模块来源、真实 DSL 调用、Podfile 解耦及文件引用、脚本真实挂载、Pods 工程完整性、约束库和业务网络入口。分别记录静态检查、依赖安装、目标工程构建、设备业务及异常回退的结果；仅安装成功不能代替构建与业务通过。本规范编制或更新时，不为验证文字而自动执行 `pod install` 或构建。

### 3.4、<span id="frontend-behavior">前端统一行为与本地演示回退</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

演示数据与正式数据隔离，界面应清楚标识当前演示状态及结果归属。演示操作不隐式补发到正式环境；涉及真实资金、审批等动作时，明确其是否实际发生。正式权限和数据验收仍按[真实业务证据要求](#evidence-classification)执行。

每个动态列表必须提供完整空态和重新加载入口；对无数据、无权限、加载失败给出相应反馈。素材默认随包提供；需要远程图片时先显示本地资源，加载失败保留本地兜底，并记录来源及许可。

## 四、<span id="backend-stack">后端技术栈与数据库</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

### 4.1、<span id="go-backend">后端语言：Go</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

后端默认使用 [**Go**](https://go.dev/)。锁定工具链、模块及依赖版本，按目标操作系统与 CPU 架构生成发布包。引入本地库或跨语言依赖时，验证相应运行库及编译要求。

普通部署优先使用经校验的预构建发布包，源码构建作为明确的独立路线；运行服务器是否需要 Go 工具链，以所选部署方式决定。

### 4.2、<span id="database-selection">数据库选型</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

以免费、开源且满足业务要求的方案为主，主业务数据库优先评估 [**MySQL**](https://www.mysql.com) 或 [**PostgreSQL**](https://www.postgresql.org/)。每个项目通常先确定一种主数据库，不要求默认同时部署多种数据库。

确需缓存、搜索、分析或其它数据存储时，说明用途、选型依据、版本、许可、资源占用、数据同步及维护责任。“免费”需分别核验软件许可、托管服务、商业支持及分发条件。

### 4.3、<span id="data-consistency">数据设计与一致性</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

关键业务明确事务边界、幂等、并发控制和失败补偿。金额采用明确精度与舍入规则；时间明确存储、时区和展示策略；删除、归档、脱敏和数据导出有可执行规则。

业务数据、文件、配置及必要元数据的备份要形成一致的恢复方案。迁移版本与应用版本关联，涉及不可逆变更时写清恢复条件。

### 4.4、<span id="api-contract">接口契约与版本兼容</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

接口文档与实现保持一致，可采用 [**OpenAPI**](https://www.openapis.org/) 等契约方式管理。明确鉴权、校验、错误码、分页、文件限制、超时、重试和限流。

移动端存在旧版本滞留时，约定服务端兼容范围与退役方式。接口及数据结构变化应进行影响分析，避免客户端与服务端发布不同步造成业务中断。

### 4.5、<span id="backend-security">认证、安全与数据保护</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

账号认证、密码安全存储、会话过期、服务端授权、敏感数据保护、上传校验及必要审计从基础级实施。按暴露面配置加密传输、最小权限、请求限制和安全更新策略。

密钥、密码、私钥及生产凭据不进入源码、普通日志或交付截图；通过受控方式配置和交接，明确轮换与撤销责任。测试数据应按实际敏感程度脱敏，避免非必要复制生产数据。

### 5.2、<span id="deployment-docs-scripts">每个目标系统对应的部署文档与脚本</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 5.2.1、<span id="deployment-documents">部署文档</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

**5.2.1.1、目标服务器最低与推荐配置。**突出 CPU 型号／能力及核数、内存、磁盘类型与可用空间、带宽、数据增长和备份空间。配置必须关联相应负载与验证依据；无法实测时标明估算及限制，不能虚构已验证最低配置。

**5.2.1.2、环境及依赖版本。**分别列出构建环境与运行环境，写明最低支持、推荐及实际验证版本，包含数据库、运行库、必要工具、网络来源、端口、权限和可选依赖。采用容器或虚拟机时注明宿主前提与额外资源。

**5.2.1.3、操作步骤与脚本工作流。**文档必须包含从获取发布包、启动入口、选择模式、配置到成功访问的具体步骤，并逐阶段解释脚本检查什么、修改什么、失败如何处理。写明配置、业务数据和日志位置，以及启动、停止、重启、状态查询、升级、回滚、备份、恢复和卸载入口。

**5.2.1.4、注意事项与故障排查。**对适用的权限、证书、防火墙、软件源、磁盘、休眠及依赖限制提供排查方法；无特殊事项可简述。涉及删除、覆盖、停机、联网暴露或数据迁移的说明属于必备内容，不能列为可选。

各系统说明应直接给出本系统所需工具、安装包、入口和命令；可链接公共解释，但不能只提供总入口链接。同步说明 API 回退、空态、图片兜底和离线演示方式。

#### 5.2.2、<span id="deployment-scripts">部署脚本</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

**5.2.2.1、系统与入口一一对应。**原则上每个目标系统提供一个清楚的部署主入口；同一入口可检测已验证版本和架构。必要辅助文件随包提供并在文档说明，不能要求用户猜测该运行哪个文件。

**5.2.2.2、面向非技术人员交互。**减少文字输入，优先使用默认值、列表、方向键、回车和空格。列表选择优先评估 [**fzf**](https://formulae.brew.sh/formula/fzf) 等适合工具，明确真实按键和依赖；进入子菜单可返回上一层，取消或空选不隐式开始部署。用户自由输入只用于确需填写的路径、域名或凭据等内容。

**5.2.2.3、完整自动部署流程。**对所选路径执行环境与数据库健康体检，发现缺失或损坏后准备必要依赖，再次检查通过后装载指定版本的后端发布包、配置、执行必要迁移、启动服务并验证访问。已有健康环境优先复用；不得无提示升级或覆盖用户现有数据库和其它业务服务。

**5.2.2.4、本地测试模式。**macOS 与 Windows 10 及以上兼容矩阵中的桌面系统必须提供“本地部署＋内网穿透”入口，与“服务器部署”通过菜单区分；具体范围和工作流见[本地部署与内网穿透](#local-tunnel)。macOS 以最新正式稳定版为主要目标，具体补丁版本在交付时核验。

**5.2.2.5、全生命周期能力。**除首次安装外，还应提供状态检查、重启、升级、回滚、备份、恢复和卸载；可通过主菜单或明确的子命令调用。重复执行不得重复初始化、覆盖数据或重复创建服务。

**5.2.2.6、来源与变更可见。**执行前展示部署对象、版本、下载来源、安装位置、端口、需要的权限和主要变更；下载与安装结果进行完整性检查。危险覆盖或删除单独确认，例如要求精确输入大写 `YES`；日志脱敏，取消与失败有明确退出结果。

**5.2.2.7、路径与失败处理。**路径根据入口或项目根目录解析，不依赖启动工作目录或开发机目录。检查权限、中文与空格路径、端口冲突和磁盘空间；关键阶段失败立即停止下游步骤并给出日志位置及恢复建议。

### 5.3、<span id="local-tunnel">macOS／Windows 本地部署＋内网穿透</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

#### 5.3.1、<span id="local-purpose">目标与适用范围</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

复用现有电脑进行临时测试、联调和演示，尽量减少云服务器支出。提供仅本机、局域网、内网穿透三种访问方式；默认启动本地服务，外部访问由用户选择并清楚展示暴露范围。

电脑关机、休眠、断网或穿透服务中断可能导致访问中断，应写入使用条件。用于长期业务时另行评估可用性、数据保护、带宽和维护责任。

#### 5.3.2、<span id="local-workflow">本地与穿透工作流</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

先完成本地环境及数据库体检、必要依赖准备、程序部署和业务自检，再按用户选择配置局域网或穿透访问。穿透成功后展示实际地址、认证方式和有效期，并验证外部访问及需要的回调。

穿透启动失败时保留已健康运行的本地服务，清楚说明外部访问尚不可用，并提供重试、诊断和关闭入口。退出和停止方式必须明确，避免遗留未说明的后台暴露。

#### 5.3.3、<span id="tunnel-boundaries">访问、第三方能力与费用边界</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

明确穿透服务、账号、免费额度或费用、流量、带宽、连接数、地址稳定性及加密认证。仅暴露必要应用入口，数据库和管理端口保持受控；凭据不写入公开地址、源码和普通日志。

登录、支付回调、小程序域名等能力按平台规则逐项验证，临时穿透地址不默认满足正式业务要求。使用脱敏测试数据，明确演示交易与真实交易的边界。

#### 5.3.4、<span id="local-migration">恢复与迁移</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

提供重启、断线重连、停止穿透、备份和恢复说明。向正式服务器迁移时，覆盖数据库、文件、配置、域名、证书和第三方回调，并明确切换窗口与回退条件。

### 5.4、<span id="deployment-recovery">升级、回滚与卸载</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

升级前核对当前版本、目标版本、迁移路径、停机要求和备份可恢复性；完成后执行健康与核心业务检查。应用回滚和数据库恢复分别设计，涉及不可逆迁移时注明停机、恢复点与可能的数据损失，经确认后执行。

卸载分别处理程序、配置、服务、穿透及业务数据。默认保留业务数据；明确选择删除时展示准确对象并单独确认，避免影响其它项目或共用数据库。

### 5.5、<span id="deployment-cost">部署成本与持续支出</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

分别列出服务器或本地硬件、电力网络、数据库服务、域名、证书、穿透、短信、邮件、对象存储、备份、第三方接口及商业支持费用。注明一次性或持续支出、计费方式、免费额度、超额处理和付款责任；不作未经核验的永久免费承诺。

## 六、<span id="engineering">工程代码与质量管理</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

### 6.1、<span id="engineering-standards">代码与模块规范</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

项目开始时确认目录、命名、格式、注释、模块边界、错误处理及日志规范。代码以可读、职责清楚和可维护为目标，注释解释必要的职责、原因和边界。

源码、配置、资源和路径具备可迁移性；环境参数与业务逻辑分离。依赖和生成流程可追溯，第三方代码与自维护代码边界清楚。

### 6.2、<span id="version-management">版本、依赖与构建</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

使用 [**Git**](https://git-scm.com/) 等版本管理记录源码和配置变化。锁定依赖，记录构建工具、命令、资源与必要环境，保证交接方能够重建约定产物；未实现逐字节一致构建时，不作该项声明。

发布包包含版本、源码版本标识、构建时间、目标系统与架构及完整性摘要。保留约定数量的已验证版本，以支持追溯和回滚。

### 6.3、<span id="quality-checks">评审、检查与自动化</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

在与项目规模相匹配的范围内执行代码评审、格式和静态检查、关键业务测试、依赖风险及秘密信息检查。自动化优先覆盖易回归、影响数据或交易正确性的业务规则，不用空洞覆盖率代替有效验证。

失败检查必须有处理结果，跳过项说明原因与影响。构建、测试和部署日志均关联对应版本。

### 6.4、<span id="documentation-consistency">文档与实现一致性</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

功能、接口、数据库、脚本入口及行为变化时，同步维护相关说明和测试。文档写清当前能力、入口、限制、失败处理和验证状态；项目内路径采用可迁移的相对引用。

## 八、<span id="operations">运维、维护与责任边界</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

### 8.1、<span id="monitoring">监控、日志与告警</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

明确服务、依赖、业务成功率、错误率、响应时间、磁盘及必要容量的检查方式和阈值。约定日志级别、保留、轮转、脱敏和查询方式；告警明确接收人、升级路径、处置及恢复确认。

健康检查同时考虑进程存活、依赖就绪和必要业务可用性，不能只根据首页打开判断全部业务正常。

### 8.2、<span id="backup-disaster">备份与灾备</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

备份范围包括数据库、业务文件和必要配置，明确频率、保留期、位置、加密、权限、容量及失败告警。依据业务确定 RPO、RTO，并通过隔离恢复演练验证完整性、耗时和业务结果。

备份成功与恢复成功分别记录。演练不得覆盖生产数据，恢复步骤、依赖、负责人和最近验证日期保持可查。

### 8.3、<span id="support-warranty">质保与维护服务</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

### 8.4、<span id="maintenance-lifecycle">容量、升级与退役</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

定期检查数据增长、资源容量、依赖生命周期、安全更新、域名证书及第三方配额。系统或组件接近维护结束时安排升级、迁移和回归；退役时明确数据导出、保留、删除、账号撤销和资源停止计费。

### 8.5、<span id="exceptions-responsibilities">例外、未完成项与责任记录</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>
