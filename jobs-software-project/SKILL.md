## 🔥 <span id="前言">前言</span>

> 接收原始需求，生成可由用户逐项补填的项目文档，再依据补填内容回归。文档工作可独立完成；进入实现后才按选定语言加载对应工程 Skill。

## 一、<span id="project-entry">入口与资源</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 可显式调用 `$jobs-software-project`；用户说“从 0 到 1 开发一个前后端项目”并给出需求时，也按本工作流处理。
- 首次编制项目文档，读取同目录[完整开发与交付规范](./软件项目开发与交付规范.md)和[项目需求与开发评审模板](./项目需求与开发评审模板.md)。两者分别提供约束与补填结构，不把通用规范当成具体项目已确认事实。
- 后续只修改某个已确定范围时，读取当前项目文档及规范命中章节；不因普通局部修复重新生成整套需求。
- 优先沿用用户指定文档、目录和既有项目基线；没有指定格式时输出 Markdown。没有项目名称时使用中性文件名，不编造项目名。

## 二、<span id="frontend-choice">前端默认原生方案</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

1、检查用户是否已明确各目标端的技术路线；明确选择原生、跨平台或按端混合时直接遵从，并保留既有项目已确认的方案，不重复询问。

2、用户没有特别说明时，对需求范围内的目标端默认采用原生方案：桌面端、移动端采用各平台原生，Web 采用标准 Web，小程序采用官方原生方案。直接记录“按 Skill 默认采用原生方案”，无需再询问原生还是跨平台，也不将默认应用写成用户逐项确认。

3、标准型指各平台原生与标准 Web；通用型示例为移动端 Flutter、桌面 Python 图形方案等，按端混合则分别记录各端路线。标准型／通用型是本文的项目选择名称，不代表正式行业分类或平台等价兼容承诺；鸿蒙等平台能力仍按目标版本核验。

4、默认原生不扩大交付端范围，也不自动确定具体原生语言、框架或版本。目标端、iOS 的 OC／Swift 等影响当前实现的选择仍不明确时，只澄清必要事项；等待期间继续整理不依赖该事项的文档，相关字段留白。

5、除本 Skill 明确的前端原生默认规则外，范本中的语言、框架、数据库和部署版本是候选或工程约束；项目尚未选择时留白，不写成“用户已确认”。iOS 原生语言确定后，必须执行[OC／Swift 蓝本与专项要求](./软件项目开发与交付规范.md#ios-native-baseline)：JobsByPods、链式＋点语法 DSL、Podfile 解耦、安装后脚本、OC Masonry／YTKNetwork、Swift SnapKit／JobsNetworking。

## 三、<span id="evidence-and-blanks">原文、留白与红字</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 信息状态 | 文档写法 |
| --- | --- |
| 用户明确提供或确认 | 准确写入，并保留来源；不扩大其适用范围 |
| 适用本 Skill 的前端默认规则 | 填写原生方案并注明“按 Skill 默认”；用户有明确指定时采用其指定方案 |
| 已核验的技术事实 | 标明依据、核验日期和版本；技术事实不等于用户选型 |
| 未提供且无明确默认规则的信息 | 字段、表格单元格或冒号后真正留空；不填“待确认”、横线、TBD、猜测值或范本候选值 |
| 有表述但含义不清、来源冲突、尚未验证的解释 | 用红字写清具体不确定点、依据和待确认内容；不能当成已经确定的要求 |

- 原始需求全文直接放入项目文档，保留原句、顺序和案例来源。澄清后的结构化解释另列，不回写篡改原文。输入含凭据等敏感内容时，遮蔽敏感值并说明处理，不复制到交付件。
- 红字统一使用 `<span style="color:#d32f2f;">【不确定 Q-001】具体内容与依据</span>`。保留文字标识和稳定编号，即使查看器不显示颜色也能识别。例：“自动处理”的触发条件和完成结果未明确；不得把缺失的数据库版本虚构成红色版本建议。
- 没有信息与不确定信息分别处理。缺失项保留字段；有依据的歧义才标红。用户后续确认或核验证据已消除歧义时，才解除对应红字。
- 硬件最低配置、性能、报价、排期、权限、表结构及第三方能力都不得凭空填入。必要推导须有依据，未经确认的推导用红字标明；建议与承诺分开。

## 四、<span id="document-generation">首次生成文档</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

1、按模板将已知需求映射到需求文档、开发评审、三级验收、前后端方案、数据库、接口、测试、部署和交接运维栏目；需求与不确定项分别分配稳定编号。

2、默认形成一份可补填的《项目需求与开发评审》主文档。用户要求分册或内容已足够复杂时，再按实际范围拆为需求、技术设计、数据库、测试或部署等文档，并保持编号和引用对应。缺少内容的栏目留白，不用通用解释填满业务字段。

3、按原始需求保留角色、权限、主流程、异常闭环、里程碑、风险及评审结构。有依据的业务流程和状态可形成图，尚不明确的分支标红；不能为填满流程而发明业务。

4、分库分表、多数据库和复杂架构按容量依据评估，不默认引入。当前版本或平台能力在需要具体判断时查询官方资料；无法核验时标红，不补写成已验证。

5、建立需求→实现项／设计→用例→验收证据的追溯结构。尚未开发时实现和执行证据留白，不声称构建、安装、联调或测试通过。

6、交付时简要指出文档位置、已采用的默认或指定前端路线及主要红字编号，方便用户依次补填。普通缺失项已经在表中留白，不把每个字段都变成连续提问。仅明确影响当前工作的关键问题。

## 五、<span id="document-regression">补填后的二次回归</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 读取用户补填的当前完整文档，与可核对的上一版比较。写前保留快照；只合并本轮确认内容，保护用户补填、原始需求和既有编号，不拿旧模板覆盖当前文档。
- 检查需求范围、角色权限、状态流程、技术选择、接口、数据、测试、里程碑、部署及验收之间是否完整、一致和可追溯。新冲突或未验证解释标红，仍缺信息继续留白。
- 逐项核对 Q 编号，已解决项按新依据更新；未解决项保留红字，不能只因用户修改了其它段落就清除。需求增删改时更新受影响设计、用例和验收项。
- 返回修订文档及简短回归结论，说明已解决、仍不确定、仍缺失和阻塞实现的事项。没有代码执行时称为文档回归，不称为测试通过。
- 若用户已要求进入实现，在前端路线及影响当前实现的业务条件明确后推进；未明确部分只开展不依赖它的工作，不把文档回归变成自动发布、采购或生产操作授权。

## 六、<span id="workflow-validation">交付前核对</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 原文和案例可溯源，原始表述与结构化解释分开，用户补填完整保留。
- 无明确默认规则的缺失字段真正留空；不确定项有红字、编号和依据；没有把默认选型当成用户逐项确认。
- 前端未特别说明时已按原生方案记录，无需再询问路线；用户指定跨平台或混合时已遵从。交付端范围、iOS 语言与蓝本、布局和网络层对应准确。
- 编号、需求映射、内链和表格有效；在支持 HTML 颜色的 Markdown 查看器中核对红字。不能预览时说明未完成视觉验证，保留红字源码与文字标识。
- 未执行的安装、构建、测试及发布不写为成功；没有本轮授权时不修改既有项目、不提交或推送。
