## 🔥 <span id="前言">前言</span>

> 接收原始需求，生成可由用户逐项补填的项目文档，再依据补填内容回归。文档工作可独立完成；进入实现后才按选定语言加载对应工程 Skill。

## 一、<span id="project-entry">入口与资源</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 可显式调用 `$jobs-software-project`；用户说“从 0 到 1 开发一个前后端项目”并给出需求时，也按本工作流处理。
- 首次编制项目文档，读取同目录[完整开发与交付规范](./软件项目开发与交付规范.md)和[项目需求与开发评审模板](./项目需求与开发评审模板.md)。两者分别提供约束与补填结构，不把通用规范当成具体项目已确认事实。
- 后续只修改某个已确定范围时，读取当前项目文档及规范命中章节；不因普通局部修复重新生成整套需求。
- 优先沿用用户指定文档、目录和既有项目基线；没有指定格式时输出 Markdown。没有项目名称时使用中性文件名，不编造项目名。
- 新建工程或规范现有项目目录时，必须读取并应用[工程目录分层与技术路线](./软件项目开发与交付规范.md#project-directory-layout)：Git 根下并列 `代码/`、`测试/`、`需求/`、`部署/`，部署不得嵌在代码内。代码、测试、需求三个主目录一级仅保留 `README.md` 与文件夹，其余资料按职责、内容或标题归档；部署按系统组织，保留实际共用的锁清单与配置。代码下分前端、后端，前端再按产品端与实际技术分层。自定义英文目录以大写字母开头，MacOS 的目录及自维护表述统一写 `MacOS`；`iOS` 专名、语言包路径及工具链固定布局等例外按[命名规则](./软件项目开发与交付规范.md#directory-naming-case)保留。不要把目录整理误作技术重选，也不新增或保留项目自维护的 `artifacts/`。
- 新建工程、规范目录或交付代码定位文档时，必须按[独立工程代码地图](./软件项目开发与交付规范.md#unit-code-maps)将地图放在具体前端／技术工程、后端实现和各系统部署单元内；各端分别维护，上层仅保留导航及必要依赖链接，不能用一张混合地图替代。共享源码只引用唯一归属；拆分时保留原有定位条目和跨端关系。
- 编制部署方案、准备开发／测试环境或实施交付时，必须应用[按机器准备环境与公共依赖边界](./软件项目开发与交付规范.md#machine-managed-environments)：按实际系统、架构和版本复检；公共 SDK、解释器、工具链与依赖放项目外的机器／用户级受管理环境，项目保留声明、锁文件、配置及准备入口。明确注明的私库、工具链最小必要缓存及发布包自包含运行依赖分别按该节界定，不沿用工程内夹带整套环境的做法。
- 进入项目实现与交付时，必须按[测试脚本与移动端双模式](./软件项目开发与交付规范.md#test-script-delivery)编写与本期实际支持端相匹配的可运行测试脚本，并附就近使用说明；移动端分别提供模拟器、真机执行模式及各自证据。仅编制需求文档时先登记计划，不伪造脚本已实现或测试已执行；普通局部修复仍按受影响范围验证，不因此重建整套项目或测试。
- 开发、测试和部署脚本遵循[自动识别与键盘选择原则](../jobs-macos-shell/SKILL.md#script-keyboard-only)：已有可用参数优先自动复用，多候选展示来源供选择，正常交互只用空格、回车、方向键和 Tab；就近文档说明实际键位、默认值和确需文字输入的原因。
- 编制或维护部署交付时，必须按[各平台一致的快捷入口](./软件项目开发与交付规范.md#deployment-shortcuts)为实际支持的每个系统提供明确标名“快捷入口”的平台启动文件，统一转交各自唯一部署实现；同步各层文档、地图及隔离测试，不能只在部分平台提供或用快捷入口复制实施逻辑。
- 每个目标系统的部署与反部署脚本必须按[成对交付及恢复规则](./软件项目开发与交付规范.md#deployment-recovery)实际提供；记录部署前后的资源归属，数据通过 fzf 选择备份（默认）或清零，不以占位说明替代反部署能力。
- 本机＋内网穿透的临时运行模式必须按[终端生命周期提示](./软件项目开发与交付规范.md#temporary-terminal-lifetime)在确认前及运行日志中红字加粗显示“关闭此运行终端，服务将结束”；纯文本环境保留原文，落盘日志不含颜色控制码，并验证退出时只回收本次服务与隧道。
- 部署输出必须按[地址与扫码入口](./软件项目开发与交付规范.md#deployment-address-qr)同时提供可复制 URL 和本地生成的二维码，各端分别标明用途；终端显示及本地二维码产物回退、实际地址更新、解码比对和手机访问分别验收。
- 各平台部署／反部署核心控制逻辑按[原生自包含要求](../jobs-macos-shell/SKILL.md#script-portable-self-contained)直接内嵌，接受必要冗余，不额外要求用户配置脚本生成环境；实际独立交付的二维码等工具按[公共组件分层](./软件项目开发与交付规范.md#deployment-shared-components)归类，调用、测试、文档与地图随实现同步。

## 二、<span id="frontend-choice">前端默认原生方案</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 检查用户是否已明确各目标端的技术路线；明确选择原生、跨平台或按端混合时直接遵从，并保留既有项目已确认的方案，不重复询问。

- 用户没有特别说明时，对需求范围内的目标端默认采用原生方案：桌面端、移动端采用各平台原生，Web 采用标准 Web，[**微信小程序**](https://developers.weixin.qq.com/miniprogram/dev/framework/)采用微信官方原生方案。直接记录“按 Skill 默认采用原生方案”，无需再询问原生还是跨平台，也不将默认应用写成用户逐项确认。

- 标准型指各平台原生与标准 Web；通用型示例为移动端 Flutter、桌面 Python 图形方案等，按端混合则分别记录各端路线。标准型／通用型是本文的项目选择名称，不代表正式行业分类或平台等价兼容承诺；鸿蒙等平台能力仍按目标版本核验。

- 默认原生不扩大交付端范围，也不自动确定具体原生语言、框架或版本。目标端、iOS 的 OC／Swift 等影响当前实现的选择仍不明确时，只澄清必要事项；等待期间继续整理不依赖该事项的文档，相关字段留白。

- 除本 Skill 明确的前端原生默认规则外，范本中的语言、框架、数据库和部署版本是候选或工程约束；项目尚未选择时留白，不写成“用户已确认”。iOS 原生语言确定后，必须执行[OC／Swift 蓝本与专项要求](./软件项目开发与交付规范.md#ios-native-baseline)：JobsByPods、链式＋点语法 DSL、Podfile 解耦、安装后脚本、OC Masonry／YTKNetwork、Swift SnapKit／JobsNetworking。

- 微信小程序作为独立前端目标，与 Web／H5 分别登记；需求包含该端时，读取[微信小程序专项要求](./软件项目开发与交付规范.md#mini-program)，在需求、实现、接口、测试、发布和交付矩阵中覆盖。支持该端不代表每个项目自动新增该端，网页预览不能代替小程序真机验收。

## 三、<span id="evidence-and-blanks">原文、留白与红字</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 信息状态 | 文档写法 |
| --- | --- |
| 用户明确提供或确认 | 准确写入，并保留来源；不扩大其适用范围 |
| 适用本 Skill 的前端默认规则 | 填写原生方案并注明“按 Skill 默认”；用户有明确指定时采用其指定方案 |
| 已核验的技术事实 | 标明依据、核验日期和版本；技术事实不等于用户选型 |
| 未提供且无明确默认规则的信息 | 字段、表格单元格或冒号后真正留空；不填“待确认”、横线、TBD、猜测值或范本候选值 |
| 有表述但含义不清、来源冲突、尚未验证的解释 | 用红字写清具体不确定点、依据和待确认内容；不能当成已经确定的要求 |

- 原始需求全文直接放入项目文档，保留原句、顺序和案例来源。澄清后的结构化解释另列，不回写篡改原文。输入含凭据等敏感内容时，遮蔽敏感值并说明处理，不复制到交付件。
- 红字统一使用 `<span style="color:#d32f2f;">【不确定 Q-001】具体内容与依据</span>`。保留文字标识和稳定编号，即使查看器不显示颜色也能识别。例：“自动处理”的触发条件和完成结果未明确；不得把缺失的数据库版本虚构成红色版本建议。
- 没有信息与不确定信息分别处理。缺失项保留字段；有依据的歧义才标红。用户后续确认或核验证据已消除歧义时，才解除对应红字。
- 硬件最低配置、性能、报价、排期、权限、表结构及第三方能力都不得凭空填入。必要推导须有依据，未经确认的推导用红字标明；建议与承诺分开。

## 四、<span id="document-generation">首次生成文档</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 按模板将已知需求映射到需求文档、开发评审、三级验收、前后端方案、数据库、接口、测试、部署和交接运维栏目；需求与不确定项分别分配稳定编号。

- 默认在外层 `需求/项目需求与开发评审/README.md` 中形成可补填的完整项目需求与开发评审，按[同目录 README 收口原则](../jobs-markdown-docs/SKILL.md#single-readme-per-directory)融合相关说明，不在核心代码中另建副本。用户明确要求独立原稿、分册或固定交付名称时遵从指定；确需拆为不同职责主题时，各主题目录以 README 承载正文，保持编号、引用及专属附件对应。缺少内容的栏目留白，不用通用解释填满业务字段。

- 按原始需求保留角色、权限、主流程、异常闭环、里程碑、风险及评审结构。有依据的业务流程和状态可形成图，尚不明确的分支标红；不能为填满流程而发明业务。

- 分库分表、多数据库和复杂架构按容量依据评估，不默认引入。当前版本或平台能力在需要具体判断时查询官方资料；无法核验时标红，不补写成已验证。

- 建立需求→实现项／设计→用例→验收证据的追溯结构。尚未开发时实现和执行证据留白，不声称构建、安装、联调或测试通过。

- 交付时简要指出文档位置、已采用的默认或指定前端路线及主要红字编号，方便用户依次补填。普通缺失项已经在表中留白，不把每个字段都变成连续提问。仅明确影响当前工作的关键问题。

## 五、<span id="document-regression">补填后的二次回归</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 读取用户补填的当前完整文档，与可核对的上一版比较。写前保留快照；只合并本轮确认内容，保护用户补填、原始需求和既有编号，不拿旧模板覆盖当前文档。
- 检查需求范围、角色权限、状态流程、技术选择、接口、数据、测试、里程碑、部署及验收之间是否完整、一致和可追溯。新冲突或未验证解释标红，仍缺信息继续留白。
- 逐项核对 Q 编号，已解决项按新依据更新；未解决项保留红字，不能只因用户修改了其它段落就清除。需求增删改时更新受影响设计、用例和验收项。
- 返回修订文档及简短回归结论，说明已解决、仍不确定、仍缺失和阻塞实现的事项。没有代码执行时称为文档回归，不称为测试通过。
- 若用户已要求进入实现，在前端路线及影响当前实现的业务条件明确后推进；未明确部分只开展不依赖它的工作，不把文档回归变成自动发布、采购或生产操作授权。

## 六、<span id="workflow-validation">交付前核对</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 原文和案例可溯源，原始表述与结构化解释分开，用户补填完整保留。
- 无明确默认规则的缺失字段真正留空；不确定项有红字、编号和依据；没有把默认选型当成用户逐项确认。
- 前端未特别说明时已按原生方案记录，无需再询问路线；用户指定跨平台或混合时已遵从。交付端范围、iOS 语言与蓝本、布局和网络层对应准确。
- 本期包含微信小程序时，已单独登记其工程、实际平台能力及验收证据；开发、体验、提审与正式发布状态分别记录，未用 Web／H5 的结果代替。
- 已进入实现与交付时，各承诺端均有实际可运行的测试脚本及就近 README；移动端模拟器、真机模式的前置条件、使用方式、报告和验收证据分别明确，未连接真机或未执行的模式没有写成通过。
- 工程目录符合[统一分层](./软件项目开发与交付规范.md#project-directory-layout)，代码、测试、需求、部署四个职责目录位于 Git 根，前三个主目录一级只有 `README.md` 和文件夹，各职责目录说明正文按 README 收口，独立原稿／阅读版等例外有明确依据，附件按职责归档；自定义英文目录首字母大写、MacOS 写法统一，固定名称例外有依据；仅创建本期实际端与技术目录，无自维护 `artifacts/` 遗留。目录迁移后已同步入口、包依赖、工程引用、忽略规则和文档，并按受影响范围验证；保留用户改动与既有技术选型。
- 代码地图正文与 `.codegraph/` 索引按实际语言、端和实施单元边界维护；纯汇总根层不保留混合索引，上层仅导航，共享源使用相对引用；地图 README、原有定位条目、跨单元关系及必要独立交付链接迁移完整。
- 各目标系统部署与反部署脚本成对可执行，部署前环境与资源归属有依据；默认备份／明确清零、取消、失败及恢复验证与实际实现一致，未用说明文档充当脚本。 各系统快捷入口齐全、名称明确、相对寻址有效并调用唯一实现；语法／隔离与原生双击验证状态分开记录。
- 目标机器环境已按系统、架构及版本核对；公共 SDK／依赖与可配置缓存不在项目内存放或随源码分发，环境路径运行时解析；私库与工具链必要例外有清单依据，安装包运行依赖和开发环境已区分。
- 部署访问地址和二维码按用途对应、内容一致，二维码离线生成且无凭据；窄终端与生成失败有回退，地址更新同步产物，解码与手机／公网验收状态分别如实记录。
- 编号、需求映射、内链和表格有效；在支持 HTML 颜色的 Markdown 查看器中核对红字。不能预览时说明未完成视觉验证，保留红字源码与文字标识。
- 未执行的安装、构建、测试及发布不写为成功；没有本轮授权时不修改既有项目、不提交或推送。
