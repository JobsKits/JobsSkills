## 🔥 <span id="前言">前言</span>

> [大前端体验主规范](../SKILL.md)涉及桌面或移动浏览器时读取本附件。业务任务与状态可以跨端共用，导航、构图、信息密度和输入方式须按 Web 推导。以下布局配方是工程经验归纳；不能把手机 App 的五个 Tab 换成五个横排按钮，就称为桌面 Web 设计。

## 一、<span id="web-archetypes">先判网站形态，再选业务骨架</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 形态 | 主要访问方式与任务 | 优先骨架 |
| --- | --- | --- |
| 公开内容／商业网站 | 从搜索、分享或外链直达；了解内容、商品或服务，再决定行动 | 品牌／全局导航、清楚页标题、正文或商品主体、相关信息与适用页脚；允许详情直接成为入口 |
| 登录后的 Web 应用 | 高频重复处理、比较、协作；经常返回同一工作上下文 | 当前组织／工作区、按职责组织的导航、内容工作区、局部工具栏、状态与账户入口 |
| 同时包含两者 | 对外介绍与发现，对内使用和管理 | 保留各自信息层级，明确“进入工作台／返回网站”等边界，不让营销导航占满工作区 |

- 登录与否只是线索，不能单独决定形态；需要登录的阅读站仍可能以内容为主，公开查询工具也可能采用应用式布局。
- 再读取命中的[商业场景模式](./business-patterns.md)，确定该页完成发现、比较、操作还是持续工作；不得看到“Web”就默认建后台仪表盘。
- 依据实际窗口可用宽度和任务所需空间选断点；设备名称、浏览器全屏状态或固定 1440 宽稿不能代替布局判断。

## 二、<span id="web-navigation">桌面导航各有职责</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 结构 | 使用条件 | 不能机械套用 |
| --- | --- | --- |
| 顶部全局导航 | 网站主要栏目少且稳定，需要跨栏目发现；常结合品牌、搜索、账户 | 不受 App 3～5 项限制，也不因栏目多就无限横排；低频项分组或按层级收纳 |
| 左侧导航 | Web 应用有持续工作模块、分组层级或工作区上下文 | 独立详情／单任务不必有侧栏；不能按数据库表生成菜单 |
| 页内 Tabs | 同一对象或同层任务的相关视图，例如商品详情／评价、订单不同状态 | 不等同 App 底部顶层导航；点击切换视图，不把立即执行的动作做成 Tab |
| 面包屑 | 用户需要理解分类／组织层级，或从深链进入后回到上级 | 表达当前位置的上级关系，不伪造为浏览历史；浅层单流程可不显示 |
| 页脚 | 公开站点的辅助导航、联系、条款、来源或版权等确有内容 | 不强迫全屏聊天、编辑器或工作台挤出营销大页脚；无限加载时重要页脚仍应能到达 |
| 账户／个人中心 | 个人资料与设置通常放账户菜单，个人任务按业务另设入口 | 不为延续 App“最后一个是我的”而新增横排末项或桌面底部“我的” |

- 桌面 Web 不默认使用底部 3～5 Tab，也不默认给每页画一条 App 式返回导航栏。顶层导航、页内视图和当前操作应能清楚区分。
- 标明当前栏目和页面标题；多个导航区域有各自明确名称。页面头部、导航、主内容及补充内容应在视觉和结构上对应，[W3C 页面区域](https://www.w3.org/WAI/tutorials/page-structure/regions/)支持这些语义区分，不规定唯一位置配方。

## 三、<span id="web-composition">按任务组织宽屏表现力</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 当前任务 | 桌面常用构图 | 表现重点与边界 |
| --- | --- | --- |
| 品牌／服务了解 | 一处明确主视觉与价值陈述，随后按疑问递进的证据、条件、行动区 | 主视觉可为真实商品、作品或情境；Hero 是主视觉区，不必是自动轮播，不把所有内容做成大幅广告 |
| 内容发现／阅读 | 入口采用有层级的标题、缩略图、摘要；详情控制正文宽度，必要时配目录或相关内容侧栏 | 用字号、图文比例和段落节奏建立重点；宽屏不等于正文跨整屏，不重复手机瀑布流充满所有页面 |
| 商品比较／购买 | 结果页可用筛选区＋商品网格，详情可左图右购买决策区，结算保持费用与输入清楚对应 | 结果数量、筛选条件及排序可辨认；仅一个商品时直达详情，不自动加入购物车和复杂分类 |
| 行情／资产判断 | 自选／对象列表、事实与图表、明细按任务分列或分区 | 让单位、时点、选中对象和变化口径对应；没有决策作用的图表和统计卡不加入 |
| IM／持续沟通 | 多会话时会话栏＋消息区；确有频繁查看对象资料需求时再加第三栏 | 正文消息维持可读行宽；单会话可只保留聊天主体，不为占满宽屏制造无效栏 |
| 运营／业务处理 | 局部搜索与筛选、可比较表格、选择／批量工具栏、详情侧板或独立详情 | 仅在确有多条同类处理任务时提供批量操作，并明确选择范围；详情复杂时不要强塞窄侧板 |

- **宽度为任务服务。** 阅读与说明控制行长，表格与比较任务适度利用宽度；多余空间可留白，不以拉伸卡片、放大字体或新增统计图填满。
- **同屏密度有取舍。** 查询／比较页让更多有效行列同时可见，详情页让主要证据和动作形成层级；不把手机的大按钮、大留白原样铺满工作台，也不把工作台压到看不清。
- **滚动边界可理解。** 公开内容通常以页面滚动为主；聊天、编辑器等需要独立滚动区时，让当前滚动对象明确，避免多个相邻小滚动框争抢滚轮。
- **粘附有目的。** 购买决策、长表头或高频工具栏确有持续可达价值时才固定；不能挡住正文、弹层、焦点和缩放后的内容。

## 四、<span id="browser-contract">浏览器是一层现成的交互系统</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 重要详情及可独立工作的页面有稳定 URL；复制链接、直接访问、刷新和重新登录后能回到相应上下文。可分享的查询词、筛选和分页按任务纳入地址，私有草稿与敏感信息不塞进 URL。
- 导航使用有真实目标的链接，提交／删除／切换控件使用相应操作语义。保留用户通过修饰键、右键或中键开新标签页的能力，不把所有跳转做成没有地址的点击容器。[MDN 链接元素](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/a)说明链接目标、键盘激活及伪链接问题。
- 默认不强迫每次跳转开新窗口；确需新窗口时让用户可预期。浏览器前进／后退能还原有意义的页面和查询状态，面包屑只表达层级，不能代替历史。
- 多标签页可独立持有筛选和编辑上下文；不能因另一页切换记录就悄悄覆盖当前未提交表单。会话到期、权限变化或并发修改时解释现状，避免用“已保存”掩盖未成功写入。
- 搜索／结果页提供清楚的查询范围、当前条件、结果数、排序和恢复入口；只有必要时才增加复杂筛选。翻页、改变排序或筛选后的结果与地址、选中项和滚动位置应一致。
- 需要定位、比较和重新找到记录时优先考虑分页或明确的加载更多；连续内容消费才判断是否适合无限滚动，保持返回定位与可达页脚。[GOV.UK 分页](https://design-system.service.gov.uk/components/pagination/)提供分页适用条件及无限滚动对键盘用户的风险，其服务建议不等于所有商业内容流都禁止无限滚动。
- 桌面刷新通过可见按钮、筛选提交或浏览器刷新完成；下拉刷新和上拉加载不作为桌面必备手势。实时更新另有明确状态，不能靠用户猜测数据是否变化。

## 五、<span id="input-and-reflow">输入方式与响应式转换</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 鼠标支持精确选择和悬停补充，键盘有可见焦点与合理顺序；重要操作不能只在 hover 后才能发现和执行，触控、键盘也有路径。快捷键、拖拽和右键菜单都是增益，不能成为唯一入口。
- 详情侧板、对话框或菜单打开后焦点与关闭方式明确，关闭后回到触发位置；非阻断状态反馈优先在相关区域表达，不用桌面中央弹窗承接所有消息。
- 文件选择、下载、复制、全屏和浏览器权限按实际宿主验证；原生 App 能调用的能力不能因为“手机 Web 长得一样”就承诺同等支持。
- 窄窗口先保留主任务和有意义的阅读顺序，折叠导航、将并排详情改为逐层进入、把筛选侧栏改为可达面板；不能仅缩小桌面稿，也不自动新增 App 底部导航。
- 需要二维关系的表格／时间轴可在其自身区域保留横向浏览，页面其余内容仍应重排；不能以一张宽表为理由让整页横向溢出。[W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)解释了重排及二维内容局部例外。
- 响应式后保持业务语义与关键内容，不把手机形态降为只能浏览的海报。浏览器缩放、长翻译和字体变大后，主动作及焦点仍应可达。

## 六、<span id="cross-surface-map">同一业务的三端映射</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 判断 | 原生手机 App | 手机 Web | 桌面 Web |
| --- | --- | --- | --- |
| 主导航 | 多个稳定目的地时可用底部 Tab | 内容站可用压缩头部／菜单；高频应用式体验才考虑底部导航 | 按网站栏目用顶栏，按持续工作模块用侧栏；不默认底部 Tab |
| 查看详情 | 通常逐层进入原生页面 | 链接可直达、刷新及浏览器回退；布局可逐层 | 可并排、侧板或独立路由，按比较频率和详情复杂度选择 |
| 个人设置 | 业务足够时可设“我的” | 账户入口／菜单或个人页，访客设置保持可达 | 常在账户菜单／独立设置区域，不必占顶层业务栏目 |
| 刷新与更多 | 适合列表时下拉／触底 | 按内容与浏览器手势冲突选择，保留显式操作入口 | 刷新按钮、查询提交、分页／加载更多按任务使用 |
| 主操作 | 安全区与键盘上方可达，常用底部操作区 | 可用底部操作区，但不遮挡浏览器及内容 | 放在对象／表单／工具栏的相应上下文，未必全局固定底部 |

例：“借鉴预约平台，只做机构活动报名的 Web 页面，不做 App”。公开活动详情可由分享直达，以活动图像、时间地点、适用对象和报名条件组织主体，右侧报名摘要承接动作；表单复杂时进入独立确认页。报名记录从账户入口找回，无需新增首页／活动／消息／我的四个底部 Tab。手机浏览时将摘要重排到主体之后或采用不遮挡内容的操作区，仍保留 URL 与浏览器返回。是否收费、名额规则和取消条件待确认，不默认补商城或审批后台。

## 七、<span id="web-checks">Web 方案与实现的核对点</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 先说明本期是公开网站、Web 应用还是两者组合；从当前页的访问入口和任务推导外壳，不直接照搬参考 App 的顶层栏目。
- 本期包含桌面 Web 时，给出桌面首屏区域顺序、主要宽度分配、列表／详情关系和操作位置；“响应式”“自适应大屏”不能代替这些具体决定。
- 对实际支持的窄、中、宽窗口分别说明导航和主要内容如何重排；不要为了展示三个宽度自动承诺三个独立产品端。
- 从外链直达一条详情，刷新、返回、新标签页打开并复制链接；检查能否独立恢复其业务上下文，未授权访问仍由权限处理。
- 搜索与筛选后的返回、分页、旧数据更新失败、空结果和内容删除各有明确恢复；不能以全局空态替换仍有效的结果。
- 表单与长任务有稳定标签、明确提交入口和可持续查看的错误；不能让用户依靠短暂提示记住要修改哪个字段。
- 仅用键盘走通主任务，再检查触屏是否遗漏 hover 才出现的操作；检查缩放、固定区域与对话框是否遮挡焦点或提交按钮。
- 方案任务只核对这些决策，实际实现后再用浏览器和截图验证；没验证过的刷新路由、文件能力和并发编辑不能写成通过。
