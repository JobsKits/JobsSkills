## 🔥 <span id="前言">前言</span>

> 本附件用于把[业务体验推导](../SKILL.md)落到可检查的方案。按任务规模压缩或展开；示例是推演方法，不是每个项目必须附加的功能清单。

## 一、<span id="contract">最小体验方案</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

先写一句任务：“角色在情境下，通过所选功能达成结果。”再按下表记录；页面可以是独立路由、原生页面、面板或弹层，不按字段数量拆页。

| 决策 | 需要落下的内容 |
| --- | --- |
| 案例与范围 | 哪些内容实际可见、取哪些功能／表现、哪些不取；不可访问的部分标明依据缺失 |
| 主线与辅助 | 采用哪类任务模式，哪些辅助模式只作用于局部页面 |
| 交付载体与骨架 | 分别声明 App／移动 Web／桌面 Web；Web 再分公开网站或持续操作型应用，写明导航与布局依据，不从参考 App 自动继承外壳 |
| 页面结构 | 每页目的、入口／返回、首屏区域顺序、主动作及结果去向 |
| 视觉方案 | 内容主角、信息密度、色彩角色、字体层级、图片比例、分组方式和空间节奏；具体 token 或既有 token 引用 |
| 状态与恢复 | 适用的加载、数据、空、错误、重试、取消、提交中、登录／权限、离线及结果未知 |
| 多端转换 | 先按已承诺载体分别给出导航与构图，再处理窗口变窄／变宽；写明浏览器 URL、刷新、前进后退，以及原生安全区、键盘等实际差异 |
| 依据与验证 | 用户已确认／体验默认／业务待确认；实际截图、操作与尚未完成的验证 |

每个必要补齐项给出一句因果：“没有 X，用户无法完成／确认／恢复 Y。”不能给出具体因果且用户未选取的业务模块，先不加入。

可复用页面条目：

| 页面／承载形式 | 谁要完成什么 | 首屏顺序与视觉主角 | 首要动作与结果 | 进入／返回 | 关键状态及恢复 | 依据 |
| --- | --- | --- | --- | --- | --- | --- |
| 按本项目填写 | 按本项目填写 | 按本项目填写 | 按本项目填写 | 按本项目填写 | 按本项目填写 | 用户明确／体验默认／业务待确认 |

业务事实缺失时保持相应业务字段为空；原型可用明确标记的样例验证布局。不要为了填满表格虚构成交量、评分、费率和退款承诺。

## 二、<span id="example-commerce">案例：只取商品详情与下单</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

输入：“参考某电商 App，只做商品展示和下单，手机与 Web 都能用。”

- 主线是交易决策，先确认卖什么以及是否需要配送；未明确前不承诺地址、运费、支付渠道或履约规则。
- 默认闭环为商品展示入口→商品详情→必要的规格／数量选择→订单确认→提交结果／订单详情。若仅一个商品，详情可直接是入口；购物车、推荐算法、会员、优惠券和卖家后台不自动加入。
- 详情首屏围绕主图、名称、价格及核心决策条件组织；App 可采用底部购买区。移动 Web 保留站点头部和浏览器返回，购买按钮按可达性决定是否吸底；桌面 Web 可用左侧画廊、右侧购买面板及顶部站点导航，账户归账户入口，不添加底部五 Tab。三端保持同一规格和金额含义。
- 有支付才加入支付选择与结果查询；提交后响应未知显示核验中，不能让用户重复创建订单。只模拟下单时明确演示，不能显示真实扣款成功。
- 空态区分商品下架／不存在／加载失败；规格不可买有原因，提交失败保留已选内容；订单结果能够返回查看，不只弹一条成功提示。

这里补的是“能决定、能提交、能找回结果”。不以“参考大型商城”为理由移植其整套业务。

## 三、<span id="example-im">案例：只取单聊与文件发送</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

输入：“参考微信，只要单聊和发文件。”

- 已有明确会话对象时可直达单聊；否则需要范围内的对象选择或会话入口，不能直接新增完整通讯录和好友关系系统。
- 会话页以消息时间线为主体，身份／连接状态次之，输入与附件操作稳定可达。App 常独立会话页；移动 Web 同时保留会话链接及浏览器历史；桌面 Web 有多会话需求时可用会话列表＋消息双栏、按需加文件侧板。不能把联系人、聊天和设置机械变成桌面底部 Tab。
- 文件选择→发送中／进度→成功或失败重试构成文件消息闭环；支持的文件类型、大小、访问与保存期限属于业务／平台条件，未知就登记，不凭示例捏造。
- 用户正在读历史时保持锚点，新消息给可点击提示；位于底部时才跟随滚动。向上取历史不套用普通信息流“下拉刷新后回顶部”。
- 消息的发送中、已接收、已送达和已读分别按实际协议展示；失败重发不产生重复消息。是否持久化和跨设备同步按范围决定，不能只因“简单版”就默认刷新丢历史。

不自动补朋友圈、群聊、钱包、全量社交关系或商业化。底部 Tab 与营销轮播对本需求没有必然价值。

## 四、<span id="example-content">案例：只取图片发布与收藏</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

输入：“参考图片社区，只做发图和收藏，页面要有活力。”

- 任务闭环为内容入口→图文详情→收藏／取消→收藏列表，以及选图→排序／编辑必要内容→发布中→发布结果。草稿恢复、裁剪等按实际必要性决定，不强加复杂创作器。
- 视觉主角是作品：根据图像差异采用有节奏的图文流或网格，保留作者和标题的阅读层级。不能只在通用文字卡片上加鲜艳按钮；不能虚构赞数、评论或推荐效果充当活力。
- 发布是动作，可放工具栏、显著按钮或中间动作入口，但不能冒充一个点击即切换的持久导航目的地。
- 收藏反馈可即时更新并在失败时回滚／说明，未登录时保留作品和操作意图；发布失败保留输入，重新进入收藏列表能确认结果。
- 不自动加入私信、关注、短视频、直播、推荐算法或广告业务；用户明确只借功能时，也不复制案例商标、配色和专有素材。

## 五、<span id="review">方案自检问题</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 去掉案例名称后，当前页面是否仍能解释它服务谁、完成什么任务？
- 去掉装饰后，内容层级和操作位置是否仍然能表达业务？
- 用户不看说明文档，能否知道下一步、结果在哪里、失败怎么恢复？
- 改成同一套通用卡片会损失哪些业务表达？若回答不了，视觉推导尚未完成。
- 新增的每个业务模块是否真为闭环所必需？演示和真实状态是否能明确区分？
