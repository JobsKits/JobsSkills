## 🔥 <span id="前言">前言</span>

> 蒸馏 App 与 Web 各自成熟的表现模式，形成 AI 可执行的设计判断：接到模糊需求，主动把选定功能补成可辨认、可操作、有表现力的前端体验。交付完整程度以用户任务能否闭环衡量，不以页面、组件或数据库表的数量衡量。

## 一、<span id="activation">触发与归属</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- “参考某 App 做其中几个功能”“照这个案例做个简单版本”“需求大概如此，页面帮我完善”等请求，即使没有说 UI／设计，也必须加载本 Skill。输入不完整不等于只交付字段表单、列表和详情三个壳。
- 这是业务体验层；[从零到一规范](../jobs-software-project/SKILL.md)负责需求、工程与交付治理，各语言 Skill 负责实现。局部功能提取可以单独使用本 Skill，不强制重走完整立项或生成整套文档。
- 先读现有需求、设计系统、页面、资源及用户指定案例。用户已有视觉或交互选择优先；明确要求像素复刻时按该目标执行，本 Skill 只补未给出的状态和适配，不擅自改版。
- 抽取的是选定能力及完成它的必要依赖，不继承整个案例的商业规模、品牌资产、后台或技术栈。没有查看到的案例只记为用户描述，不能编造其实际页面和行为。
- 工具类产品不建立行业模板；命中既有业务模块时只复用相应模块。纯后端和明确的小修只处理本期范围。

## 二、<span id="reasoning">先推导体验，再拆实现</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

**页面方案 = 业务主线 × 交付载体（App／移动 Web／桌面 Web）× 用户角色与阶段 × 内容形态 × 操作风险 × 使用情境；品牌与文化用于调节表现。** 这是决策框架，不是行业审美定律。同一业务常有稳定的信息顺序和交互骨架，不能据此推出唯一配色、布局或动效。

先读取[商业场景模式](./references/business-patterns.md)中命中的条目。先确定主线，再按需要组合辅助模块：商品详情中的客服复用 IM，会话不因此变成全产品首页；内容中的付费复用交易，不能因此增加完整商城。

| 推导步骤 | 必须得到的判断 |
| --- | --- |
| 提取范围 | 案例来源、选取功能、用户原话、明确排除项；区分功能借鉴与视觉借鉴 |
| 选择载体 | 先确认本期 App、移动 Web、桌面 Web；Web 再区分公开浏览型网站与持续操作型应用，先选择相应骨架再填业务；不能从参考 App 推出目标 Web 也采用 App 外壳 |
| 找任务闭环 | 谁在什么情境下，看什么、决定什么、做什么；完成后在哪里确认结果、继续或返回 |
| 补必要依赖 | 缺少哪项入口、详情、状态反馈或恢复路径会使选定功能不可用；只补这些依赖 |
| 组织页面 | 页面目的、首屏主角、主动作、进入／离开方式、登录时机和关键状态；不按数据库表直接生成菜单 |
| 确定表现 | 内容主次、密度、构图、字号层级、色彩角色、图像和动效语义，以及各端差异 |
| 落地验证 | 方案任务检查正常及恢复路径；原型／开发任务再落实到原型或代码，并核对目标尺寸实际呈现 |

采用[方案记录与推演示例](./references/experience-contract.md)记录决策；小任务可在回复或现有需求中紧凑表达，大任务写入既有前端章节，不强制额外创建文档。本轮只要求方案时，交付可检查的页面与视觉决策；要求原型时制作原型；要求开发时继续实现。主动补齐不改变本轮交付形态，不能停在未落实的泛泛建议。

## 三、<span id="completion-boundary">主动补齐的边界</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 内容 | 处理方式 |
| --- | --- |
| 用户明确指定的功能、视觉与约束 | 直接采用，保留出处，不被模板覆盖 |
| 让选定任务成立的页面和反馈 | 主动补齐，标为“体验默认／必要依赖”，说明简短依据，不要求用户逐控件确认 |
| 未指定但可逆的视觉决定 | 给出一个与业务一致的具体默认方案；原型／开发任务中据此实施，现有项目优先沿用其设计系统 |
| 金额、权限、收费、退款、时限、资质等业务规则 | 不擅自确定；只在影响当前实现时集中澄清，独立工作继续推进 |
| 优惠券、积分、分销、会员、社交关系等增长能力 | 未选中且非必要依赖则不加入，仅有价值时简短列为建议 |

- 在需求文档里区分“用户已确认”“体验默认”“待确认业务”；后者按从零到一规范留白或标红，不用模板补成事实。演示商品、价格和人数标为样例，不伪造成真实经营数据。
- 选取局部功能不必具有完整 App 外壳：单会话可以直达聊天页，单商品可以直达详情；不为凑 3～5 个 Tab 制造无用页面。
- 用户未限定风格时主动决策，不能以“需求不够清楚”为由把全部视觉工作推回给用户。只有会改变业务含义、成本或选取范围的缺口才需要澄清。

## 四、<span id="expression">把表现力变成具体设计</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- **选主角。** 首屏应有明确的业务焦点：金融是可信金额与动作，内容是作品，IM 是会话和消息，交易是商品与决策条件。栏目不应全用同尺寸、同权重卡片。
- **确定层级和节奏。** 主信息、辅助解释、操作与状态各有位置；决定何处密、何处留白、何处大图或连续列表。只有分组或交互边界需要时才加卡片，不把每行内容都装进圆角盒子。
- **用内容表达业务。** 商品用有意义的图像与规格；社区用作者、作品和讨论；金融用金额、趋势、时间和来源。演示内容覆盖真实长度、不同状态与信息密度，不能全用“测试数据”。
- **定视觉参数。** 用已有 token 或明确的新 token 表达色彩角色、字号与字重、间距、圆角、边界、图片比例和交互状态；写清本方案为何这样选。只写“高级、活泼、简洁”不构成方案；避免无关渐变、大阴影和仪表盘填充。
- **动效服务动作。** 区分进入／返回、状态变化、直接操控和结果确认；同层切换与层级推进具有稳定空间关系。需制作动效时读取 [motion-design](../motion-design/SKILL.md)的相关时序与缓动指导，按当前交互复杂度选用；简单状态反馈不强制主／次／环境三层，背景循环不构成交付要求。登录切换可复用 [Jobs 登录注册动效](../jobs-auth-switch-motion/SKILL.md)。弱化动效时仍能理解和完成任务。
- **把张力用在合适位置。** 内容、商品和品牌区可以鲜明；资金确认、订单金额及错误恢复以准确、可读为先。地区和文化只作具体受众的调节依据，不用国籍刻板印象替代产品判断。

## 五、<span id="interaction">按载体选择交互与表现模式</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

业务任务、交易事实、身份和错误恢复属于共通体验；导航、空间组织、浏览器行为和输入方式必须按载体分别决定。

| 载体／层次 | 加载与设计要求 |
| --- | --- |
| 共通业务体验 | 读取[交互默认与失效边界](./references/interaction-patterns.md)，采用命中的身份、内容、状态、反馈与支付规则；不能把其中移动端外壳当作所有端的默认 |
| App | 在确有多个高频同级目的地时采用底部 Tab；按原生导航栈、安全区、返回手势和键盘组织页面 |
| 移动 Web／H5 | 同时读取[Web 独立表现模式](./references/web-patterns.md)；可借鉴 App 的触控与单列阅读，但保留 URL、浏览器前进后退和刷新；底部 Tab 需由高频目的地证明必要，不因手机访问自动添加 |
| 桌面 Web | 必须读取[Web 独立表现模式](./references/web-patterns.md)，先按网站／Web 应用选择顶栏、侧栏与内容布局；不默认底部 3～5 Tab、首页轮播、最后“我的”、下拉刷新或居中手机画布 |

同一商业模式应分别推导各载体的页面骨架，不能先套 App 再删几个控件就视为完成 Web 设计。已有同产品跨端设计系统时复用语义和品牌，仍按浏览器及窗口情境适配。

- 命中普通内容轮播或设置入口时，必须读取[交互默认](./references/interaction-patterns.md)：轮播保留自动与手动切换，不放开启／暂停／继续控件或数字页码；默认当前实心、其余空心，自定义也须有两种明显不同的标识。独立设置按钮默认使用齿轮图标，并保留本地化无障碍名称。
- 命中账户入口、登录注册／找回密码或后台页面时，必须读取同附件的[共通账户边界](./references/interaction-patterns.md#shell-and-navigation)：完整提供三条门路径，已登录资料替换登录／注册入口，设置通常收口一次；正式后台强制登录，明确 Demo 后台按其例外免登录进入，调试连接设置只在 Demo 展示。
- 共用用户任务、业务事实和主次优先级，不要求各端沿用同一组件顺序与页面数量。按窗口空间及输入能力重组导航、列表、详情和操作区；窗口变窄不等于变成原生 App，大屏也不等于只能鼠标操作。
- 沿用全局 API 优先与演示回退合同，见[前端统一行为](../jobs-software-project/软件项目开发与交付规范.md#frontend-behavior)。已有真实数据遇到失败时保留上下文，演示结果与真实结果隔离；演示资金和消息不能冒充真实完成。
- 全局三主题与十语言是基础交付约束：白天／黑夜／跟随系统；简体中文、繁体中文、藏文、英文、日文、法文、西班牙文、德文、俄罗斯文、韩文。验证长文案、字体回退、金额日期格式及切换后布局，不用只翻译菜单冒充完整支持。
- 素材沿用全局来源和本地打包规则；无素材时先查 iconfont，用户明确指定来源优先。不得以来源不明图、无意义色块或虚构经营数据填满画面。

## 六、<span id="verification">验收与交付</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- **范围检查：** 每个补齐项都能解释如何帮助选定功能闭环；没有复制案例的全量业务，没有自动增加交付端。
- **体验检查：** 从入口到结果／返回可操作；成功、空、失败、重试、取消、未登录／过期等适用状态语义清楚。没有死按钮、假支付或只能靠自动消失提示理解的错误。
- **账户与环境检查：** 按[共通账户验收](./references/interaction-patterns.md#shell-and-navigation)分别核对游客、登录与退出／过期，完整门路径及资料替换；正式后台和明确 Demo 的进入方式分别验证，断网与鉴权失败不能扩大权限。
- **视觉检查：** 从实际截图能辨认主角、主动作与业务类型；层级、内容、图像、密度和动效已具体落实，不只是在通用 CRUD 页面换主色。
- **适配检查：** 按实际支持范围检查小屏、大屏、键盘弹出、字体放大、主题及语言切换；逐端核对导航和构图是否确有依据。桌面 Web 不套手机外壳；移动 Web 不丢浏览器能力。Web 检查链接／深链、刷新、前进后退、多标签页、鼠标／触控、键盘与焦点，原生端检查安全区、返回及系统手势。
- **现有运行入口检查：** 修正用户正在使用的界面时，先定位实际网址或应用、构建产物目录及服务加载来源；源码和临时预览通过不能代替该入口的修复。按本轮授权重建并更新实际加载的产物，保留可回退副本，再从原入口刷新验证；Web 可对比服务返回资源与新产物哈希排除旧包。只完成源码、尚未更新产物时必须明确说明，不能宣称运行界面已经修正，也不因此扩大到未授权的发布范围。
- **如实记录：** 已实现界面必须启动并查看关键页面截图，必要时迭代；未能运行或缺少目标设备时说明未完成的验证。仅产出方案就称方案检查，不写成视觉或真机验收。
- 最终简述采用的业务模式、主动补齐的关键页面／状态、文件位置及实际验证结果。专项规则以本 Skill 为唯一维护处，调用者只保留入口。
