## 🔥 <span id="前言">前言</span>

> 适用于所有工程和语言。减少可在提交前发现的 CI 错误，以实际提交、目标运行环境和远端运行结果交付。平台限制和未执行项必须保留证据边界；不能承诺永不失败，也不能把推送成功当作 CI 通过。

## 一、<span id="scope">先确定本次检查范围</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 修改前读取仓库规则、相关 workflow、复用链、被调用脚本及最近一次有关运行的完整失败步骤。记录当前分支、实际远端、已有工作区／暂存区改动和相关基线；沿用源码所有权边界。
- 从真实配置列出本次应触发的 workflow、事件、分支／路径过滤、job、矩阵维度、`needs` 和关键检查，核对分支保护所需的检查名称。区分必须执行项、配置原本允许的条件跳过项与未覆盖项；不固定步骤数量，不要求无关的手动发布 workflow 自动运行。
- 明确 runner 系统／架构、shell 和参数、语言／SDK／依赖版本来源、工作目录与依赖准备方式。核对版本、action 输入、弃用项、runner 镜像和平台语义时查询当前官方资料，不凭本机缓存或记忆猜版本。
- 代码写法按命中的语言 Skill；维护 `run:` 脚本时同时遵循 [脚本规范](../jobs-macos-shell/SKILL.md)及其目标平台片段。Git 仓库布局按 [仓库规范](../jobs-git-repository/SKILL.md)，不复制语言或仓库专项规则。

## 二、<span id="pre-push">提交前必须完成的检查</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 对新增／修改的 workflow 使用 [**actionlint**](https://github.com/rhysd/actionlint) 或项目已有的等价 Actions 语义检查，覆盖表达式、事件、依赖、复用调用及输入输出；普通 YAML 能解析不等于 Actions 合法。对变更脚本做目标解释器语法检查，并执行仓库要求及本次影响范围内的有效检查。工具不可用时先找现有可用方式，如实标明缺项，不能把人工阅读冒称机器校验通过。
- 从干净检出可获得的内容核对：脚本／action 路径与大小写、执行位、工作目录、锁文件、子模块／大文件、安装步骤、缓存未命中、生成依赖、打包资源和制品路径。源码目录迁移时，同步核对 workflow 的事件 `paths`、输入目录、输出／制品路径及回写目标；以实际非空生产输入运行生成器，并验证缺失或空输入明确失败，不能只校验 YAML 或目录名。不得依赖未跟踪文件、本机预装 SDK、用户配置或旧构建产物；忽略的必需二进制须有随仓源码与明确的构建准备步骤，并排在使用该产物的依赖安装／编译之前。存在显式包清单或受信 helper 基线的工程，新增／迁移本地包时须审阅实际包与 helper 后对账清单、指纹及依赖图，并从候选树执行生产门禁；不能只校验 workflow 或盲目登记新哈希，既有拒绝未知／篡改输入的负向检查仍须有效。命中原生或平台差异时，必须读取 [目标平台核验要点](./目标平台核验要点.md)的相关部分。
- 构建中的图标／资源生成器以派生构建目录承接输出，核对编译／打包阶段实际读取新输出及脚本输入输出声明；不能只迁移生成文件而仍引用旧资源。命中源码冻结门禁时，在冷／重复构建及相关配置验证产物正确、被跟踪源码不变，不能将正常构建写回源码加入豁免。明确维护源资产的独立生成命令按其既有合同处理，与构建阶段分开。
- 证明最终拟提交内容接受了检查。含并发／无关改动或部分暂存时，在隔离目录物化候选树并执行检查，记录 tree OID 与最终提交树核对；临时索引只用于构造候选，不能建了索引仍测试原脏工作区。构建所需但未发布的依赖必须暴露，不能悄悄混入提交。后续改动使证据失效时重跑受影响检查。
- 对新增／修改的执行器、管道、测试聚合器或退出码包装，至少验证真实成功、子命令失败及失败后的控制流；依赖失败结果的打包／发布不得继续，独立检查可继续收集但汇总必须失败。涉及取消／超时／清理时补对应路径。复用有效测试，不为 YAML 注释或低影响格式变更新增同义测试。
- 长流水线须核对各阶段目录的生产者、后续消费者和磁盘峰值，包含源码构建缓存、测试中间产物、最终产品及压缩包同时存在的空间。重型阶段和打包前记录可用空间、仅本次自有目录体积；在消费者结束后精确回收专用中间产物，保留源码、成品、原始结果与后续必需输入，并记录前后回执。清理入口须校验真实路径、所有权与符号链接边界，验证有效回收、证据保留、路径逃逸拒绝和失败传递，不能清系统 SDK、全局缓存或其它任务目录。空间不足时应在 worker 仍能写日志／上传的阶段有界失败；关键已完成结果在后续大体积阶段前归档，不能只依赖末尾的 `always()` 上传抵抗 runner 崩溃。
- 新增／迁移测试时，从真实 target 成员枚举类与测试方法，和显式期望清单逐项对账；按真实测试源核对指纹文件集合，保持类／方法名只改实现的变更也必须让缓存失效并被运行中来源守卫识别。在昂贵编译／矩阵前执行同一库存门禁。执行器、缓存复用、实际结果计数与报告生成绑定同一份清单，拒绝缺项、未知项和重复项；不能只放宽数量阈值，或把当前发现值直接当成期望来掩盖遗漏。
- 核对事件的凭据与权限上下文、复用 workflow 的权限交集及外部输入进入命令的方式。权限只满足实际任务，不为修失败扩大到全局写权限、泄露 secret，或让来自不受信任 PR 的代码在高权限上下文执行。

## 三、<span id="execution-contract">执行与失败传递不可失真</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 按 [官方 shell 执行规则](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsshell)核对实际包装命令、错误选项及退出码；尤其注意管道、子进程、预期非零的负向测试和日志转存。输出 `PASS` 或写出报告不能代替进程成功，首个真实失败不能被最后一条成功命令覆盖。
- 多脚本聚合必须逐项取得并立即检查各自结果；测试内部预期失败与测试执行器失败分层处理，必要时用独立进程隔离。不得用无条件 `exit 0`、清空错误状态、`|| true` 或 `continue-on-error` 掩盖必需检查；项目原本明确可选的任务和有断言验证的预期失败保留真实语义。
- `if`、`needs`、矩阵 `fail-fast`、并发取消和结果汇总须符合预定检查范围。汇总 job 成功不能抵消上游失败、未预期跳过、被取消或缺失的矩阵项。日志和失败制品应可定位问题，收集／清理失败不得遮蔽原始业务失败。主命令与 `ensure`／源码一致性检查同时失败时，并列记录主命令原始退出状态及后置错误，按声明的汇总合同失败；受影响执行器须验证“仅主命令失败、仅后置检查失败、两者同时失败”，不能只在完整制品中才能发现首错。
- 测试夹具须符合生产输入协议并隔离语言、用户配置、环境、时间和路径依赖。面向本地化界面的断言按固定语义key经产品国际化API生成完整期望文案（含格式／标点），对中文和英文做真实对照；稳定标识不翻译，不能以锁死CI语言或弱化文本匹配掩盖问题。新增／修改夹具时记录实际解释器路径和版本，按 CI 目标版本执行完整受影响夹具，不能以本机默认解释器的语法或成功结果代替；目标日志未记录版本时不得从镜像标签推断精确版本，应补无敏感信息的版本诊断。命中 Hash／关键字等调用协议差异时，以原失败和修正后正向对照验证支持版本，显式保持原输入结构。需要 SDK／工具自带字体等资源时，从当前执行工具或包配置解析资源位置；不默认存在本机 SDK 管理器的项目链接。运行环境改用其它安装入口时，在缺少该本地链接的隔离候选中验证真实资源可读及受影响断言，不能以本机完整测试通过代替此检查。修复失真的夹具或必要的生产缺陷；不得为了迁就夹具放宽路径、归档、身份、取消等保护，不得靠全局替换系统命令的 mock 改变被测模块语义。命令替身的解释器／SDK 启动链须独立于被替换工具，避免初始化回调同名替身形成递归；夹具子进程使用独立进程组、整体预算和仅限本次资源的回收，并验证悬挂子命令确实有界失败。父进程退出或管道 EOF 不代表后代已退出；TERM 后复核自有组的同 UID、非僵尸存活成员，仅仍存活时升级 KILL。ESRCH／EPERM 只在复核已无存活成员时作为退出竞态处理，真实回收失败保留原超时原因并独立失败；验证 TERM 足够与后代忽略 TERM 两条路径。

## 四、<span id="evidence">区分本地证据与目标环境证据</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 本地语义／语法检查、本地业务测试、模拟 runner、真实目标 runner、真实桌面／设备或发布环境分别表述。异系统、不同运行时及被条件跳过的分支不能用本地成功外推为兼容；模拟 runner 也不等同托管环境。
- 有目标环境时优先验证影响最大的差异。缺少目标环境仍先完成可执行的本地检查，明确剩余项；已获准推送时，可用最小且已审阅的远端 CI 变更补验证，不设置“首次推送前必须已有该提交远端绿灯”的循环前提。
- 远端验证前说明目的和当前未验证范围；这不是绕过本地可完成检查的理由。只按现有授权执行，不借 Skill 自动获得推送、发布、部署、付费资源或外部通知权限；已明确授权的动作不重复索取确认。

## 五、<span id="diagnosis">失败后先收证据再修改</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 对照出错提交、运行尝试、job／步骤及原始日志，区分配置／依赖准备、脚本／业务、夹具与权限／服务故障；读取首个真实失败及必要上下文，不只看末尾退出码。步骤超时时同时对账 job／step 与执行器内部 build／test 的预算，外层允许时长不会覆盖子命令上限；按实际阶段标记区分设备启动、冷 SDK 模块编译和运行探针，标题不能代替根因。静默日志不足以区分编译／链接活动与停滞时，补有界阶段日志及本次自有进程采样，不能仅凭未出现编译错误推断构建缓慢；进程仍有CPU活动只证明活跃，不证明会收敛或加长后的期限一定足够。分开记录累计构建期限与被中断阶段的实际执行区间，串行多配置及必要收尾同时核对外层预算。新增前置门禁和诊断回执须进入实际失败归档清单；缺少原始回执时，只标控制流推断，不能写成产物已核。混合准备阶段争用同一预算时，可保留全部验收并拆成独立有限预算与显式输出交接，分别验证，不靠有界重试掩盖稳定的预算缺口。推测须标为推测，未验证的异常机理不得写成根因或长期规则。
- 每轮修改针对可解释的失败，先做可用的最小复现和受影响回归；同源副本、调用方和包清单一并对账。前置失败可能遮蔽后续检查，修好一处后仍须走完整个必需检查范围。
- runner 自身崩溃时并列核对 run、check、步骤和 annotation；终态失败与残留 `in_progress` 步骤可同时出现，不能据后者推断命令仍在运行。已证实磁盘耗尽但缺目录体积时，不猜最大占用目录或某个打包子命令的退出码；空日志 ZIP、404 或零制品只证明原件不可取得，保留有界复查回执，不补造测试计数、来源指纹或成功产物。
- 同一失败签名重复且没有新证据时，停止重复猜改推送，转向目标环境最小探针或完整诊断。签名结合运行时、job／步骤、失败阶段及首个真实异常／断言判断，不能只按末尾 `exit 1` 归类。明确临时基础设施故障可有界重试一次；再次同因失败则保留证据并转诊断／报告，不无限重跑，不通过升级权限、跳过门禁或改远端设置换绿。
- 不得擅自删测试、减矩阵、改触发过滤、加跳过条件、放宽断言或关闭保护来取得绿灯。确需按用户要求调整检查范围时，说明行为变化并按新范围验收；允许保持验收契约的夹具修正及 job 拆分，不把拓扑或测试写法冻结为永远不能修改。

## 六、<span id="publish-verify">获准推送后的完成定义</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 只发布获准的仓库、分支和相关内容，审阅最终提交差异并确认它与已验证候选一致；保留无关改动、原有暂存语义和并发工作。不能因“修 CI”自动更新父仓 gitlink、其它远端、Tag 或 Release；推送会自动触发的发布／部署也须在已有授权范围内。
- 核对远端目标引用指向预期完整提交 SHA；定位该次事件与提交对应的所有必需运行，记录 run 链接／ID、尝试次数和 `head_sha`。PR 合成合并提交、复用／后续触发 workflow 按实际提交关联追溯；自动回写生成物后重新读取目标 HEAD，不能用回写前提交的绿灯代替最终版本。使用 `GITHUB_TOKEN` 的回写通常不会触发新的 push 工作流，须按[官方触发语义](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)核对凭据和事件；既有授权内可对最终引用执行已有的 `workflow_dispatch`，再验证运行的 `head_sha`，不能假定机器人提交会自动复验。旧提交的绿灯、旧尝试或单个 job 不能替代本次验收。
- 等待所有必需 job／矩阵及关键检查完成并确认结果成功，按第一节清单对账；未触发、排队、进行中、失败、取消、超时或未预期跳过均不算完成。配置预期的条件跳过须列明，不能混称全部执行成功。
- 用户要求“修好并推送／保证 workflow OK”时，在授权范围内继续修复和复验直到上述条件满足。必须由用户补充的访问权限、密钥、环境审批、额度或范围外决策阻塞时，报告具体阻塞及已完成内容。发布／部署等有副作用的重跑先核对幂等性和既有结果，授权不覆盖时不重做。
- 最终简要给出提交、运行链接、必需检查结论和仍未验证范围。仅本地修改就写“本地验证通过，远端未验证”；远端证据齐全才写“Actions 通过”。创建本 Skill 不等于已审计或修复历史工程。

## 七、<span id="failure-distillation">每次失败必须复盘并回写本 Skill</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 任何工程的 workflow 在当前任务中出现或被发现失败，都必须在同一任务结束前完成复盘、蒸馏并回写本 Skill，无须用户再次提醒；不能以修复后变绿作为唯一收尾。已获准的本地规则维护继续执行，不据此扩大 Git 发布或其它外部操作授权。
- 对照失败证据与修复验证，提炼“什么条件触发、为什么现有检查没拦住、以后必须增加什么检查或执行约束、怎样证明有效、适用范围与例外”。跨项目约束修订主文件，平台细节修订对应附件；只维护当前有效做法，不把仓库名、run ID、临时日志、敏感数据或事故流水账堆进 Skill。
- 回写前搜索现有同义规则，优先补强原条款及其验证要求。问题源于现有规则未被执行时，补强漏掉的触发入口、执行门禁或验收证据；原条款已完整覆盖时，按机制合并对应反例及验证条件，不能仅改日期或换措辞打卡。不能以“规则已经有了”为由省略改进，也不能重复追加同一句禁令。
- 根因尚未证实时，仍须把已证实的诊断方法、证据不足时的禁止判断和后续验证条件收进适用条款；未解决状态及原始证据留在项目记录，不把假设写成长期结论。后续证实后及时修订，不能将临时服务故障泛化为必须永久换源、提权或重构。
- 回写后核对元数据、相对链接、适用范围及规则是否实际约束本次失败路径；涉及执行器或验证方法时复用最小复现与负向对照确认效果。永久记忆只登记长期决策及规则入口，避免复制完整 Skill；最终简要说明改了哪条规则、验证结果和仍待确认项。
